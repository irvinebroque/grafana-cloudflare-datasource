# Cloudflare platform coverage

Reviewed on 10 November 2026 against plugin 0.1.2, the live SQL catalog, live GraphQL introspection, the implementation, and current public documentation.

## What the existing validation establishes

The 91/95 successful dataset queries measure the SQL catalog returned for the validation account. They are **not a percentage of Cloudflare platform coverage**. Two entries in that catalog are account-defined Analytics Engine tables. Catalogs can change by account and deployment, and Log Explorer datasets appear only where enabled. A successful empty result establishes query/frame compatibility, not a complete product integration. See Cloudflare's [SQL dataset discovery contract](https://developers.cloudflare.com/analytics/sql-api/datasets/).

The plugin also accepts raw GraphQL queries. Live schema introspection through the plugin exposed 257 account fields and 64 zone fields, including metadata fields, overlapping variants, and staging nodes. These counts are not counts of supported products or accessible production datasets. Schema presence does not establish plan access, useful results, or adequate editor support. Cloudflare documents [introspection and account/zone settings](https://developers.cloudflare.com/analytics/graphql-api/features/discovery/) for determining those separately.

The SQL builder and its discovery/completion cover SQL datasets. There is no equivalent GraphQL dataset browser or product query builder today; GraphQL's starter query is for Workers. Operational REST APIs are not query sources: the existing resource routes only discover accounts, zones, and SQL datasets.

## Highest-value gaps

1. **Discover and guide GraphQL products.** Start with DNS/DNS Firewall, dedicated firewall/WAF events, Load Balancing/Health Checks, Container resource metrics, Gateway, Magic Transit/WAN, AI Gateway, AI Search, and Durable Object storage. Reuse the existing GraphQL backend and catalog-driven UI approach. Prefer SQL where equivalent datasets exist. Exclude staging/deprecated nodes from default suggestions and consult account/zone settings for availability.
2. **Handle the full range of log schemas.** SQL can discover account-specific Log Explorer datasets, but native logs are primarily designed and tested for Workers and Containers. Builder fallback columns assume their schema, and native context/volume helpers are restricted to those two products. Other logs may use different timestamps/message fields, have no log level, or have no meaningful context identity. Add dataset-aware defaults and mappings, then validate enabled R2, AI Gateway, HTTP/firewall, Access/Gateway, audit, and other log datasets. Do not equate catalog discovery with complete Explore support.
3. **Add narrow, read-only operational queries.** Certificates, pool/origin health, tunnel status, deployments, inventory, and Audit Logs v2 fill a different gap from analytics. Use explicit allowed endpoints and typed query options rather than arbitrary URLs. Current resource snapshots do not reconstruct historical state; history needs a recorded metric/event source.
4. **Add examples, dashboards, and meaningful validation for existing SQL coverage.** Many products above already execute through the plugin but lack useful starting points. Prefer examples generated from current provider metadata over a separate adapter for every product.

## Data that belongs in another collection path

Cloudflare documents [Prometheus metrics exposed by `cloudflared`](https://developers.cloudflare.com/tunnel/observability/). These are emitted on the connector host and require scraping and storage. Grafana's Prometheus datasource is the appropriate query path after collection; querying the central Cloudflare API cannot recover those host-local metrics.

Similarly, logs exported to R2/S3/Loki or spans exported to an OpenTelemetry backend are not automatically queryable through this plugin. Using their existing Grafana datasource avoids adding a second log or metrics storage system here. This does not prevent querying equivalent data retained in Cloudflare's own analytics/observability APIs.

Add live validation where the account has the product and record unavailable/empty products separately. Keep a distinction between API execution support, guided product support, and nonempty end-to-end validation.
